# Architecture

## System shape

Groove is currently a static Vite single-page application. `frontend/index.html` provides the document shell, `frontend/src/main.ts` creates `GameApp`, and `GameApp` coordinates the audio, chart, engine, renderer, input, import, storage, and UI layers. There is no runtime server API or server database.

```text
index.html -> main.ts -> GameApp
                         |-- audio/       audio clock and playback
                         |-- analysis/    DSP, tempo/beat analysis, worker boundary
                         |-- chart/       chart types, generation, parsing, validation
                         |-- game/        input state, judgment, score, simulation
                         |-- renderer/    Three.js scene, highway, notes, effects
                         |-- import/      file decoding, import flow, optional OGG export
                         |-- storage/     IndexedDB song library and local preferences
                         `-- ui/          panels, HUD, overlays, orientation and touch
```

## Web Audio timing

`audio/AudioEngine.ts` owns the `AudioContext`, decoded `AudioBuffer`, buffer source, gain, and playback lifecycle. `audio/PlaybackTimeline.ts` maps `AudioContext.currentTime` to song time while accounting for pause, resume, seek, and chart offset. Gameplay reads this audio-derived clock; render frames do not define judgment time. This keeps visual frame-rate variation from changing note timing.

The browser initially suspends audio until a user gesture. The UI creates or resumes the context from an interaction before playback or decoding. `audio/DemoSynth.ts` generates the built-in original track with `OfflineAudioContext`, so no bundled demo recording is required.

## Music import and decoding

`import/MusicImport.ts` validates the selected blob, reads its bytes, and asks a `BaseAudioContext` to decode it. `import/ImportFlow.ts` sequences decoding, analysis, generation, validation, and optional persistence while reporting progress. `import/OggExport.ts` provides optional browser-side OGG transcoding through `wasm-media-encoders`.

The local file is processed in the browser. There is no upload endpoint. Decoding support ultimately depends on the browser's media codecs even when the file has an MP3 name or MIME type.

## Analysis and worker processing

`analysis/AnalysisClient.ts` is the asynchronous boundary. It normally creates the module worker in `analysis/analysis.worker.ts`, sends the decoded channel samples, receives progress, and returns an `AnalysisResult`. If workers are unavailable or fail to start, it can run the same analysis inline.

`MusicAnalyzer.ts` orchestrates pure DSP modules:

- `Fft.ts` supplies frequency-domain transforms.
- `OnsetDetector.ts` derives band-aware spectral flux and onset candidates.
- `TempoEstimator.ts` evaluates tempo and phase candidates.
- `BeatGrid.ts` measures alignment, beat coverage, bar phase, and section confidence.
- `EnergyProfile.ts` identifies energy levels and quiet ranges.

The analysis layer is deterministic for the same decoded samples and options. It does not use render timing or the live audio clock.

## Difficulties

A difficulty is a bundle of facts in one table (`chart/Difficulty.ts`): how many lanes the highway
renders, which keys sit on them, the score weight, and the generation budgets (target and maximum
density, minimum note and lane gaps, chord and hold ratios, maximum chord size, SPACE budget).

| Difficulty | Lanes | Keys | Weight | Lane colours |
|---|---|---|---|---|
| Easy | 4 | A S K L | ×1.0 | 1 2 1 2 |
| Normal | 5 | A S SPACE K L | ×1.5 | 1 2 O 2 1 |
| Hard | 7 | A S D SPACE J K L | ×2.0 | 1 2 1 O 1 2 1 |

Hard's generation row is the phase 2.1 generator's own defaults, verbatim, and Hard draws the base
import seed rather than a derived one (`seedForDifficulty` in `chart/DifficultySet.ts`); those two
facts are what make its seven-key chart byte-identical to the one the earlier build produced, which
`tests/difficulty-parity.test.ts` asserts against a chart generated by the v0.2.1 code itself. Easy
and Normal are strictly simpler adaptations of that baseline (lower density, wider minimum spacing,
fewer chords and holds, never a chord wider than the baseline's two notes).

`chart/LaneProfile.ts` answers the lane-mapping question per lane count: which lane means "the beat"
(none on four lanes — the accent pair S/K takes it), which lanes each role may walk, and which lane an
onset's spectral band may fall back to. Keeping that in one module is what stops the picker, the
generator, the input map, and the score model from disagreeing about what a difficulty means.

`chart/DifficultySet.ts` runs the generator once per difficulty from a single analysis and returns a
chart set plus per-difficulty validation. Each difficulty draws from its own derived seed, so the
charts are independent but reproducible.

## Beatmap generation

`chart/ChartGenerator.ts` turns measured onsets, beat evidence, energy, and section confidence into chart events. Candidate selection avoids inventing dense grid notes where the audio does not support them. Musical-role heuristics map register and metric position to lanes through the active lane profile, with spacing, chord, density, and playability constraints. The seed and generator version are recorded for reproducibility, and the generator has no difficulty-specific code path beyond the settings and profile it is handed.

Chords are bounded twice: `maxChords` limits chord *events* (the phase 2.x rule, `floor(N · ratio / 2)`), and `maxChordNotes` limits chord *notes* so a larger `maxChordSize` widens an accent without buying more of them. With the baseline's two-note chords the event budget alone binds, which is what keeps the realised chord share exactly `maxChordRatio`.

`ChartTypes.ts` defines the versioned beatmap shape; a chart carries its own `laneCount`, `keyLabels`, `noteDensity`, and `maxScore`. `ChartValidator.ts` is the trust boundary for generated, stored, or externally supplied charts, and checks lanes against the chart's own lane count. `PatternParser.ts` supports the authored built-in pattern, while `demoChart.ts` supplies the built-in chart (the hand-authored seven-key chart, presented as Hard).

## Scoring

`chart/ScoreModel.ts` defines the arithmetic once for three callers: the live score manager, the chart
layer (which states a chart's theoretical maximum before it is played), and the tests.

```
note score = round(basePoints[judgment] × units × (1 + 0.01 × min(combo, 100)) × difficultyWeight)
accuracy   = (300·PERFECT + 200·GOOD + 100·BAD) / (300 × judgedNotes)
maxScore   = perfectRunScore(notes, difficultyWeight)      # a simulated flawless run
```

The difficulty weight multiplies points only, so accuracy and grades stay comparable across
difficulties. A hold's tail is scored at the multiplier its head was awarded at, so a hold's value
does not depend on when inside its release window the player let go.

`maxScore` is not a closed formula but a *simulation*: `perfectRunScore` walks the notes in chart
order through the same `awardPoints` arithmetic the live scorer uses (combo 1, 2, 3 … capped at 100,
tails at their head's combo). That makes the maximum exactly the score of a perfect playthrough, so
the score/max percentage in the HUD reaches 100.00 % — the earlier `units × 300 × 2 × weight` bound
assumed the capped 2× multiplier from the first note and was unreachable.

## Rendering and gameplay

`game/GameEngine.ts` advances gameplay from song time and coordinates judgments and misses. `JudgmentEngine.ts` applies timing windows; `ScoreManager.ts` maintains score, combo, accuracy, and counts; `LanePressTracker.ts` prevents duplicate logical presses; and `InputManager.ts` translates keyboard and pointer state into lane transitions.

The renderer is deliberately separate from scoring. `renderer/SceneManager.ts` owns the Three.js scene and frame-loop integration. `CameraFraming.ts` and `Layout.ts` calculate responsive geometry. `LaneRenderer.ts`, `NoteRenderer.ts`, and `EffectRenderer.ts` display the highway, chart state, and feedback. A dropped or delayed frame changes presentation but not the audio-clock judgment calculation.

`Layout.ts` is also the single source of truth for two things the brief called out:

- **Lane colours.** `LANE_PALETTES` holds the two three-colour themes and `laneColorRoles` the exact
  pattern per lane count (Hard `1 2 1 O 1 2 1`, Normal `1 2 O 2 1`, Easy `1 2 1 2`). Notes, hold
  heads and bodies, receptors, lane strips, the HUD key strip and the touch pads all read
  `laneColorsFor`, so no surface can assign a lane an independent colour.
- **Hold geometry.** `holdGeometry` produces a hold's head z, tail z, body centre and body length
  from the note's own chart timestamps through `zForTimeToHit` — one function for both the falling and
  the held state (the latter anchored at the hit line). Both ends are clipped to the visible
  playfield, so a hold longer than the road is cut at the spawn plane rather than stretched across it,
  and the body always ends exactly where its two caps are drawn.

## Input and judgment

Keyboard input maps the active difficulty's keys to lanes (`game/InputManager.setKeyLayout`) and ignores repeat events. Keys belonging to *another* difficulty never judge, but are still suppressed so SPACE cannot scroll the page on a four-lane chart. Switching layout releases everything held, so a lane cannot survive the switch stuck down.

Touch uses pointer events through `ui/TouchSurface.ts`; each pointer owns at most one lane, enabling chords and independent holds. The surface rebuilds its columns for the chart's lane count and resolves a point to a lane from rectangles cached at layout time, so a swipe judges where the finger lands on four-, five-, and seven-lane layouts alike. Cancellation and leaving the playable area release state to avoid stuck holds.

The engine compares a press or release song time with chart-note time. PERFECT, GOOD, BAD, and MISS windows are centralized in game configuration and are tested independently of rendering.

## Storage and persistence

`storage/SongLibrary.ts` uses an IndexedDB database named `seven-keys` (version 2) with four object stores: `songs` (one record per song, holding the chart set, tempo/grid values, compact diagnostics, validation data, and metadata), `audio` (the optional original or transcoded blob), and `scores` / `score-attempts` for high scores. Keeping blobs separate makes library listing inexpensive; writes span the song stores in one transaction.

`storage/SongRecord.ts` encodes, decodes, versions, and validates persisted records. Version 2 stores a map of charts keyed by difficulty; a version-1 record's single seven-key chart is migrated to `charts.hard` on read, unchanged, and the other difficulties are left absent rather than invented. Stored records are treated as untrusted input when read.

`storage/ScoreStore.ts` keeps the best run per song *and* difficulty, keyed `"<songId>::<difficulty>"`, together with an attempt count. Each entry records the score version, the difficulty weight it was earned with, and the generator version of the chart, so a later balance change cannot rescale stored history. Deleting a song deletes its scores.

If IndexedDB is unavailable, a memory implementation preserves the workflow for the current session only. `storage/SettingsStore.ts` stores small versioned preferences in `localStorage` and tolerates access failures.

Browser storage belongs to the site's origin and local browser profile. It is not a shared application database and never reaches the static hosting server.
